业务洞察

1优惠站的结构性矛盾：每一次访问都要买，用户却属于商家

贵司海外站点把访客经联盟链接送到商家完成购买，收入在商家成交后按佣金结算。站点当前以匿名访客为主：没有登录、没有账户，买家关系沉淀在商家侧。能留在贵司手里的只有两样资产——订阅了 Web Push 的浏览器，和留下邮箱的访客。订阅者的每一次免费回访，直接替代一次付费点击；本方案的九条旅程只做一件事：把这两样资产建起来、用起来、留下来。

01

旅程 1｜首访即订阅

优先级最高建立触点Deal 浏览事件触发 · 应用内软提示 · Web Push

软提示在访客看过 Deal 详情或复制过券码之后才出现，此时订阅的理由是具体的「这类好价再上新时提醒我」。浏览器原生弹窗一旦被拒绝就无法再次请求，软提示把这个机会留在贵司手里。

建议渠道：Web Push 应用内消息　｜　触发方式：事件「页面浏览」（页面类型为 Deal 详情或券码页）　｜　退出条件：事件「通知权限开启」即退出

旅程编排示意图
业务痛点
  • 首页原生弹窗被浏览器安静通知机制抑制，访客看不到请求
  • 被拒绝一次的域名无法再次请求授权，机会只有一次
  • 没有订阅的访客离站后，再次触达只能重新买流量
旅程组件配置
  • 开始组件：事件「页面浏览」触发，事件属性「页面类型」等于 Deal 详情或券码页；用户属性「通知权限状态」等于未请求
  • 再次进入：退出后可再次进入，间隔 7 天，最多进入 3 次——三次未订阅即不再提示
  • 提前退出：事件「通知权限开启」（SDK 自带埋点）
  • 转化统计：事件「通知权限开启」，监听窗口 1 天
  • Web Push 应用内消息：站内软提示，文案带当前浏览的类目名变量；点击后由页面调用浏览器原生授权
  • 等待：固定 1 天后结束；未订阅者由再次进入规则在 7 天后再提示
  • 交接：订阅成功的用户由旅程 2 承接
  • 埋点：页面浏览、通知权限开启由 Web SDK 上报；「页面类型」「通知权限状态」由站点写入
预期效益参考

访客订阅率 5% → 8–10%

增量 = 订阅者数 × 月回访次数 × 外跳率 × 每次点击收益，代入贵司联盟后台数据即可测算；订阅者每多一成，其余旅程的覆盖同步放大一成。

02

旅程 2｜订阅后欢迎与兴趣建档

见效最快首次回访订阅事件触发 · 次日按类目分流 · Web Push

订阅后的第一条消息即时发出，让用户立刻看到订阅能得到什么；第二条放在次日晚间、按首访时浏览的类目分流，同一份热门榜不再发给所有人。

建议渠道：Web Push 通知消息　｜　触发方式：事件「通知权限开启」　｜　退出条件：事件「外跳点击」即退出

旅程编排示意图
业务痛点
  • 订阅后 7 天内没有第二次访问的订阅者，之后基本不再回来
  • 欢迎推送落在用户的凌晨，被系统免打扰吞掉
  • 首访看的是电子产品，收到的却是全站热门
旅程组件配置
  • 开始组件：事件「通知权限开启」触发；不可再次进入
  • 提前退出：事件「外跳点击」
  • 转化统计：事件「外跳点击」，监听窗口 3 天；收入统计：事件「联盟转化回传」+ 佣金金额，监听窗口 30 天
  • Web Push 通知（第一条，即时）：今日 Top 3 好价，点击打开首页
  • 等待：1 日历日 → 可发送时间：终端时区 18:00–21:00
  • 条件分支：属性「兴趣类目」非空 / 为空
  • Web Push 通知（第二条）：非空一支推该类目当日好价（Webhook 取数填变量），为空一支推全站热门
  • 埋点：通知权限开启由 Web SDK 上报；「兴趣类目」为站点按近 30 天浏览计算写入的列表属性
预期效益参考

订阅后 7 日回访点击 +30–50%（相对）

依据是分层推送对未分层的点击率倍数（第 2 节）；起点以贵司当前欢迎推送数据为准。

03

旅程 3｜邮箱捕获

建立第二条通道建立触点属性触发 · 站内软提示先行 · Web Push 应用内消息 + 通知

只向已订阅且近 7 天活跃的人要邮箱，用「每周一份按你的兴趣挑的好价」作为交换。Web Push 收不到的场景（浏览器关闭、设备离线）由邮箱接住，两条通道互为备份。

建议渠道：Web Push 应用内消息 · Web Push 通知　｜　触发方式：属性「已订阅 Push」且「邮箱为空」且「最后活跃距今不超过 7 天」　｜　退出条件：事件「Newsletter 订阅」即退出

旅程编排示意图
业务痛点
  • Web Push 只在浏览器运行时可达，离线用户无第二条通道
  • 站内没有给访客留邮箱的理由，表单转化停在个位数
  • 大促日的重要消息只靠一条通道，展示不到就等于没发
旅程组件配置
  • 开始组件：用户属性「已订阅 Push」为真，且「邮箱」为空，且「最后活跃时间」距今不超过 7 天（窗口上限避免存量一次涌入）
  • 再次进入：退出后可再次进入，间隔 30 天
  • 提前退出：事件「Newsletter 订阅」
  • 转化统计：事件「Newsletter 订阅」，监听窗口 1 天
  • Web Push 应用内消息：用户在站时展示，文案带兴趣类目变量，点击打开邮箱表单
  • 等待：固定 7 天 → 可发送时间：终端时区 18:00–21:00
  • Web Push 通知：周报预告一次，点击打开表单；之后结束，不再追加
  • 交接：留下邮箱且勾选同意的用户进入旅程 9
  • 埋点：「Newsletter 订阅」事件由表单提交上报，同时写入邮箱与「Email 同意」属性；「已订阅 Push」由通知权限开启事件回写为属性
预期效益参考

订阅者留邮率 2% → 5–7%

起点取弹窗留资的公开区间下沿；提升来自只向活跃订阅者提出、且给出明确交换物。

04

旅程 4｜关注类目上新

回访主引擎回访与外跳商品层事件按人触发 · 终端时区 · Web Push

上新是商品层的变化，不是用户行为。贵司系统在某类目有新 Deal 时，只为近 30 天浏览过该类目两次以上的订阅者逐人上报一个事件，旅程进入即发，谁收到哪条由他自己的行为决定。

建议渠道：Web Push 通知消息　｜　触发方式：事件「关注类目上新」（携带类目、Deal 标题、折扣）　｜　退出条件：事件「外跳点击」且类目相同即退出

旅程编排示意图
业务痛点
  • 全站群发的上新对多数订阅者无关，点击率不到 1%，退订随之上升
  • Deal 的有效期以小时计，隔天的周报赶不上
  • 凌晨发出的推送与晚间发出的推送，展示与点击差一个量级
旅程组件配置
  • 开始组件：事件「关注类目上新」触发，事件属性携带类目、Deal 标题、折扣、落地页
  • 再次进入：退出后可再次进入，间隔 1 天——同一用户每天最多一条上新
  • 提前退出：事件「外跳点击」，属性过滤类目等于本次进入的类目
  • 转化统计：事件「外跳点击」，监听窗口 1 天；收入统计：事件「联盟转化回传」+ 佣金金额，监听窗口 30 天
  • 条件分支：属性「最后活跃时间」距今不超过 30 天 / 超过 30 天——超过者不发，直接结束
  • 可发送时间：终端时区 09:00–21:00
  • Web Push 通知：标题与正文插入 Deal 标题、折扣变量，变量支持默认值兜底；点击打开该 Deal 落地页
  • 埋点：「关注类目上新」由贵司 Deal 系统按用户上报；「最后活跃时间」由 Web SDK 页面浏览更新
预期效益参考

推送点击率 0.84% → 5–8%

自动化触发对标准群发的公开区间（第 2 节）；只发给近 30 天活跃者同时抬高送达与展示的分母质量。

05

旅程 5｜券码到期提醒

外跳直接产出回访与外跳复制券码触发 · 多实例按券并行 · 等待至到期前一天 · Web Push

复制了券码却没有外跳的用户，意向已经表达。每张券一个独立实例，锚定该券的到期时间在前一天提醒一次；用户同时复制三张券，三个实例各自计时、各自退出。

建议渠道：Web Push 通知消息　｜　触发方式：事件「复制券码」（携带券 ID、商家、到期时间）　｜　退出条件：事件「外跳点击」且商家相同即退出对应实例

旅程编排示意图
业务痛点
  • 复制券码后离站的用户，多数忘了这张券的存在
  • 券码有效期各不相同，固定节奏的群发对不上任何一张
  • 同一用户手里多张券，只能按人提醒不能按券提醒
旅程组件配置
  • 开始组件：事件「复制券码」触发，事件属性携带券 ID、商家、到期时间、落地页
  • 再次进入：可同时多次进入（多实例），并发上限 5，两次进入最短间隔 10 分钟；等待事件与提前退出的属性过滤右值插入本实例的券 ID
  • 提前退出：事件「外跳点击」，属性过滤商家等于本实例商家
  • 转化统计：事件「外跳点击」，监听窗口 2 小时
  • 等待至：事件属性「到期时间」前 1 天；时刻已过（券期不足一天）时直接退出
  • 可发送时间：终端时区 09:00–21:00
  • Web Push 通知：券码与商家名变量，点击打开该商家券页；到期即结束，不再追加
  • 埋点：「复制券码」「外跳点击」由站点上报；到期时间为券数据自带字段
预期效益参考

券码复制到外跳的转化，按贵司数据校准

有明确截止时点的提醒是 Web Push 点击率最高的一类；约半数点击发生在推送后 1 小时内（第 2 节）。

06

旅程 6｜外跳后同店追加优惠

外跳直接产出回访与外跳外跳事件触发 · 发送前 Webhook 取券 · Web Push

外跳后的 24 小时是同店二次意向最高的窗口。次日晚间发送前，先调贵司接口取该商家当前最佳券，有券才发、无券即止，消息里的折扣永远是当下真实的。

建议渠道：Web Push 通知消息　｜　触发方式：事件「外跳点击」（携带商家）　｜　退出条件：再次发生同商家「外跳点击」即退出

旅程编排示意图
业务痛点
  • 外跳后用户在商家侧比价、犹豫，站点对这段时间毫无触达
  • 预先写进推送的折扣到发送时已过期，损伤信任
  • 同一用户一天外跳多家商家，只有最近一家值得追
旅程组件配置
  • 开始组件：事件「外跳点击」触发，事件属性携带商家、类目
  • 再次进入：可同时多次进入（多实例），并发上限 1，达到上限时替换最早进入的实例——新的外跳即重置流程
  • 提前退出：事件「外跳点击」，属性过滤商家等于本实例商家
  • 转化统计：事件「外跳点击」，监听窗口 1 天；收入统计：事件「联盟转化回传」+ 佣金金额，监听窗口 30 天
  • 等待：1 日历日 → 可发送时间：终端时区 18:00–21:00
  • Webhook：向贵司 Deal 接口取该商家当前最佳券（券码、折扣、落地页），响应字段提取为旅程变量
  • 条件分支：Webhook 返回的券码非空 / 为空——为空直接结束
  • Web Push 通知：商家名与折扣变量，点击打开该商家券页
  • 埋点：「外跳点击」由站点上报；Deal 接口由贵司提供
预期效益参考

同店二次外跳率，按贵司数据校准

对照返利平台购后 24 小时个性化推荐邮件的公开案例（转化 8%），机制相同：在意向最高的窗口给出当下真实的替代选择。

07

旅程 7｜大促日历分流

对齐黑五大促战役分群全量进入 · 等待至统一时刻 · 兴趣分流 · Web Push + Email

大促当天不是一次群发，而是同一时刻按兴趣类目分四路发出不同内容；当天未点击的人晚间换一次文案，有邮箱者同时收到邮件版。整套配置复制即可用于 Prime Day、网一与圣诞。

建议渠道：Web Push 通知消息 · Email 模板消息　｜　触发方式：分群「近 90 天活跃订阅者」　｜　退出条件：事件「外跳点击」即退出

旅程编排示意图
业务痛点
  • 大促日所有站点都在推送，同一份群发在通知栏里被覆盖
  • 按组织时区发出的一条消息，落在西海岸用户的凌晨
  • 当天未点击的人没有第二次机会，而黑五的流量只有一天
旅程组件配置
  • 开始组件：用户分群「近 90 天活跃订阅者」，发布时全量进入；不可再次进入（每个大促建一条）
  • 提前退出：事件「外跳点击」
  • 转化统计：事件「外跳点击」，监听窗口 3 天；收入统计：事件「联盟转化回传」+ 佣金金额，监听窗口 30 天
  • 等待至：指定时刻，大促当天 06:00，终端用户时区——各时区用户都在自己的早晨收到
  • 条件分支：属性「兴趣类目」包含电子 / 时尚 / 家居 / 其余为默认分支
  • Web Push 通知：四路各自的大促精选，Webhook 取数填变量
  • 等待事件：1 天内等待「页面浏览」；已浏览一支结束
  • 可发送时间：终端时区 19:00–21:00 → 条件分支：属性「Email 同意」为真 / 为假
  • Email 模板消息 / Web Push 通知：换文案的当晚提醒各一条；之后结束
  • 频控：大促日 Web Push 每日上限在测试计划第 2 周统一设定，本旅程优先级设为最高
预期效益参考

大促日点击率约为群发的 1.3–2 倍

分层推送对未分层的公开倍数区间（第 2 节）；第二轮换文案的增量另计。

08

旅程 8｜沉默订阅者唤回

保护送达质量订阅留存属性触发 · 一条 Push 一条 Email · 之后停发

沉默 14–21 天是订阅者从「暂时没来」变成「不会再来」的分界。这条旅程只在这个窗口触达一次，之后停发——继续给长期不活跃者发送，只会拉低整体送达与展示。

建议渠道：Web Push 通知消息 · Email 模板消息　｜　触发方式：属性「最后活跃时间」距今 14–21 天　｜　退出条件：事件「页面浏览」即退出

旅程编排示意图
业务痛点
  • 长期不活跃的订阅仍在发送名单里，拉低送达率与展示率
  • 无差别的召回推送是退订的第一来源
  • 只有 Web Push 一条通道时，离线用户永远收不到召回
旅程组件配置
  • 开始组件：用户属性「最后活跃时间」距今超过 14 天且不超过 21 天，且「已订阅 Push」为真
  • 再次进入：退出后可再次进入，间隔 30 天
  • 提前退出：事件「页面浏览」
  • 转化统计：事件「页面浏览」，监听窗口 5 天
  • 可发送时间：终端时区 18:00–21:00 → Web Push 通知：该用户兴趣类目本周最佳三条（Webhook 取数）
  • 等待：固定 3 天 → 条件分支：属性「Email 同意」为真 / 为假
  • Email 模板消息：为真一支发一封；为假一支直接结束。两支之后均不再触达
  • 埋点：「最后活跃时间」由 Web SDK 页面浏览更新
预期效益参考

月退订率 30% → 20%

分层推送对标准推送的退订率公开区间（第 2 节）；停发长期不活跃者同时抬高其余旅程的送达与展示。

09

旅程 9｜Email 兴趣周报

第二通道的主用途订阅留存分群进入 · 每周四早间 · Webhook 取数 · Email

周报不是一份 Newsletter 群发给所有人，而是每人一份按兴趣类目实时取数的邮件：电子类订阅者收到本周电子好价，时尚类收到时尚好价，没有兴趣记录的收到全站榜。

建议渠道：Email 模板消息　｜　触发方式：分群「有邮箱且 Email 同意为真」　｜　退出条件：事件「邮件退订」即退出

旅程编排示意图
业务痛点
  • 群发 Newsletter 的点击率随列表增长持续下滑
  • 邮件内容在发送前几天就已排定，好价到达时已过期
  • 邮箱资产没有固定节奏的使用场景，留下也很快沉默
旅程组件配置
  • 开始组件：用户分群「邮箱非空且 Email 同意为真」，发布时全量进入、之后满足即进入
  • 再次进入：退出后可再次进入，间隔 7 天——每周一封
  • 提前退出：事件「邮件退订」，同时由站点把「Email 同意」写为假
  • 转化统计：事件「外跳点击」，监听窗口 3 天；收入统计：事件「联盟转化回传」+ 佣金金额，监听窗口 30 天
  • 可发送时间：每周四 08:00–11:00，终端用户时区
  • Webhook：按属性「兴趣类目」向贵司 Deal 接口取本周 Top 5，响应字段提取为变量；兴趣为空时接口返回全站榜
  • Email 模板消息：标题与五条好价全部为变量，变量支持默认值兜底；每封带退订链接
  • 埋点：「邮件退订」由 Email 通道回调上报；Deal 接口由贵司提供
预期效益参考

周报点击率对照群发 Newsletter，测试期验证

自动化流程邮件以 5.3% 的发送量贡献 41% 邮件收入（第 2 节）；本旅程以点击与外跳为主指标，不以打开率为准。
