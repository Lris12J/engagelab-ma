一、业务洞察：Zendure 的增长结构，与 MA 的四个切入点

Zendure 的收入是一条四级引擎：主机套装（€500–1,500）获客 → 扩展电池（€500–1,400/块，可堆至 17kWh+）拉客单与毛利 → ZenWave 动态电价订阅（德国已上线）赚持续服务收入 → 积分与推荐降获客成本。 当前这条链路上的每个转化节点，仍主要靠用户"自己想起来"。 在德法竞争白热化、获客成本上升的背景下， 9 万 DAU 的存量用户是回报最确定的增长杠杆。

四、数据整合与用户画像：把"埋点"升级为"可运营的用户资产"

把用户行为数据变成可分群、可触发、可归因的运营资产， 需要一套面向旅程设计的埋点体系。我们建议按"采集 → 画像 → 编排"三层架构落地， 由交付团队基于智能硬件行业模板输出完整埋点方案——第 1 周完成方案确认与接入， 让首批旅程从一开始就跑在完整的数据地基上。

① 数据采集层 · 多源汇入
  • App SDK：设备绑定、发电/充放行为、固件状态、订阅状态、App 启动
  • 官网 Web SDK：页面浏览、加购、发起结账、Web Push 订阅（无需改造官网业务功能）
  • 订单数据：商城订单事件（品类、金额、SKU）通过事件上报 / API 汇入
  • 生态数据：App Push 触达行为同源；客服与 AI 机器人会话记录可协同（同一产品生态）
② 用户画像层 · 统一档案
  • 设备资产：主机型号、扩展电池数量、总容量、固件版本
  • 能源行为：近 30 天满充天数、弃电量、日均发电、AI 模式是否开启
  • 商业价值：累计订单数、累计金额、最后下单时间、订阅状态
  • 生命周期：未激活 / 活跃 / 沉默 / 流失；语言与国家；渠道订阅授权状态
  • 多设备档案（对象数组属性）：一个用户名下的多台设备，以对象结构逐台存储型号、容量、固件、满充天数，支持分设备筛选、计算、判断与消息变量下发
  • 属性支持数值、文本、日期、布尔、列表与对象数组，支持"距今超过 N 天""每年当日"等日期运算
③ 旅程编排层 · 自动触达
  • 事件触发（弃购、支付、绑定）+ 属性筛选（满充天数、沉默天数）双入口
  • 等待事件 / 条件分支 / 可发送时间等组件零代码编排
  • 智能分群圈选高价值人群，条件分流对比验证策略优劣
  • 每条旅程独立统计发送、送达、点击、转化次数与收入金额

落地原则：服务型触达先行
阳台光储用户社区的高频话题集中在固件更新、设备连接与售后响应上。因此建议 App Push 渠道以服务型内容打头（安装引导、发电报告、设备健康检查、固件更新前置通知），先让用户建立"这个品牌的推送是有用的"的信任，再逐步叠加促销型触达——这既是转化效率问题，更是保护推送订阅与品牌口碑的关键。

场景 1｜高客单弃购挽回（官网商城）

见效最快 首购转化 结账事件触发 · 三段递进 · Email + Web Push

用户走到结账最后一步却未支付时，自动开启一段约三天的挽回序列——先答疑、再算收益账、最后限时提醒，在整个决策周期内持续解决顾虑。

旅程编排示意图
业务痛点

€500–1,500 的客单，用户不会冲动下单：反复比价、担心安装、纠结容量——高客单品类弃购率普遍在 70% 以上。

每一单弃购，都是已付出广告成本、走到最后一步的高意向用户；而官网当前没有系统性的挽回序列。

高客单弃购挽回的关键不是催促，而是持续解决顾虑：先答疑、再算账、最后才是限时提醒。

旅程组件配置
  • 开始组件：事件"发起结账"触发（可再次进入，间隔 7 天）
  • 提前退出：事件"订单支付成功"→ 立即退出
  • 等待事件 1 小时：监听"订单支付成功"→ 已支付自然转化，全程不打扰
  • Email 1（超时未支付）：购物车保留确认 + 高频顾虑答疑（安装难度、保修、退换）——刚触发 1 小时内直接发送，无需可发送时间
  • 等待事件 24 小时：监听"订单支付成功"
  • 可发送时间 09:00–21:00（终端时区）+ Email 2：按购物车内容生成收益测算（预计年发电、回本周期）+ 真实用户评价背书
  • 等待事件 48 小时:监听"订单支付成功"
  • 可发送时间 + Web Push 兜底：库存 / 限时权益提醒
  • 转化 + 收入统计：监听"订单支付成功"，统计时间 3 天（对齐旅程跨度）

场景 3｜设备数据驱动的扩容推荐（明星场景）

智能硬件独有杠杆 复购 / 客单提升 满充+夜间放空属性触发 · 型号分流 · App Push + Email

当设备数据显示"白天电池早早充满、晚上又提前放空"时，自动向用户算清两笔账——中午白扔的电、晚上多买的电，并推荐匹配的扩展电池。

旅程编排示意图
业务痛点

扩展电池是客单与毛利贡献最大的复购品类（单套可堆至 17kWh+），但购买靠用户"自己意识到不够用"——社区里最典型的故事是"用了一个夏天才发现白天存满、晚上不够用"。

两头同时发生才是真痛点：中午在白扔免费的电，晚上在花钱买贵的电——一块扩展电池同时解决两头。

  • 等待事件 3 天：监听"浏览扩容页面"，区分意向层级
  • 已浏览未购：可发送时间 + Email（扩容收益测算 + 老用户专属价）
  • 未浏览：可发送时间 + Email（月度弃电报告："这个月你放弃了约 X 度电 ≈ X 欧元"）
  • 等待事件 5 天：监听"配件订单支付成功"→ 已购退出 / 超时结束
  • 变量下发：Push 与 Email 文案通过设备对象属性注入具体设备名、满充天数与弃电量——多设备家庭可精确到"哪一台该扩容"

场景 5｜沉默用户分层召回

留存挽回 分层经营 沉默属性触发 · 设备与订单状态三层分流 · Push + Email + Web Push

对 30 天未打开 App 的用户按"已绑定设备 / 已购未绑定 / 未购买"三层分流——分别收到发电报告与健康检查、安装协助补救、政策科普与入门优惠。

旅程编排示意图
业务痛点

17 万注册与 9 万 DAU 之间是一个持续流动的沉默池，由三类人构成：

① 绑定了设备却不再打开——设备离线、故障或新鲜感消退，流失与差评的前兆；

② 下单了却没完成绑定——安装卡住后放弃，最该补救的一群；

③ 注册了却未购买——研究型下载的潜在买家与退货用户。

三类人分别需要服务关怀、安装补救、教育转化——同一套文案只会三头不讨好。

旅程组件配置
  • 开始组件：属性"最后打开 App 距今超过 30 天"触发（可再次进入，间隔 30 天，对齐进入阈值）
  • 条件分支：按属性"是否已绑定设备 + 是否有订单"三层分流
  • 已绑定设备路径：可发送时间 18:00–21:00 + App Push——月度发电报告（"你的系统上月发电 X 度 ≈ 省 X 欧"），唤回价值感 → 等待事件 5 天（监听"App 启动"）→ 已回归退出 / 仍沉默 → 可发送时间 + Email：设备健康检查 + 固件更新提示（顺带排查设备离线）
  • 已购未绑定路径：可发送时间 + Email——安装协助（"设备还没装好？"分步教程 + 在线客服入口，与场景 2 的激活引导衔接）→ 等待事件 5 天（监听"设备绑定成功"）→ 补绑成功退出 / 仍未绑定结束并保留人工关怀标记
  • 未购买路径：可发送时间 + Email——本地政策与收益科普 + 入门套装推荐 → 等待事件 5 天（监听"App 启动"）→ 已回归退出 / 仍沉默 → Web Push 限时入门优惠兜底
  • 提前退出：事件"设备绑定成功"→ 立即退出（补绑完成即达成最高目标）
  • 转化统计：监听"App 启动"，统计时间 5 天（对齐旅程跨度）
预期效益参考

召回回归率 15-25%（行业参考），显著高于无差别群发。

隐性价值：主动发现离线与故障设备——在用户带着怨气找上门（或直接差评）之前完成服务闭环。

场景 6｜NPS → 公开评价 → 推荐裂变

低成本获客飞轮 口碑增长 绑定 30 天触发 · 评分分流 · App Push + Email + 客服协同

设备用满一个月时自动发起满意度调查——高分用户被引导去公开评价并推荐好友，低分用户在写下差评之前先转给客服解决问题。

旅程编排示意图
业务痛点

该品类的转化高度依赖公开评价分数，而现状往往是：不满的用户主动去写，满意的用户保持沉默。

NPS 是 App 内的私密满意度问卷（0–10 分"你有多愿意推荐"），分数不对外公开——先私下识别满意度，再分流：满意者受邀去公开平台以自己的账号亲自写评价，不满者先转客服。

品牌已有 ZenWatts 积分体系，缺的是在"最满意的时刻"自动完成三件事：识别满意度、导流评价与推荐、在公开发声之前拦截不满。

旅程组件配置
  • 开始组件：属性"设备绑定时间距今超过 30 天"触发（不可再次进入——一次性满意度里程碑）
  • 可发送时间 18:00–21:00 + App Push：NPS 问卷邀请（1 分钟评分，完成得积分）
  • 等待事件 3 天（多分支）：分支一 = 事件"提交 NPS 评分"且分数 ≥ 9；分支二 = 事件"提交 NPS 评分"且分数 ≤ 8；默认 = 超时未提交
  • 高分路径：可发送时间 + Email——邀请前往公开评价平台亲自撰写评价 + 推荐好友双向奖励（积分 / 优惠券）
  • 等待事件 7 天：监听"推荐链接注册"→ 推荐成功发放双向奖励 / 超时结束
  • 低分路径：Email 致歉与主动服务——同步客服团队人工跟进（客服系统协同），先解决问题，不做任何营销；问题解决后同样开放评价入口，避免"只邀好评"的选择性邀评合规风险
  • 未提交路径：可发送时间 + App Push 提醒一次（积分激励），不再追发
  • 转化统计：监听"推荐链接注册"，统计时间 7 天
埋点要求（此旅程的关键前提）

· NPS 问卷需在 App 内或自有 H5 页面实现，提交时上报事件"提交 NPS 评分"（携带分数属性）——旅程监听的是应用上报的自定义事件，使用第三方问卷工具且无埋点对接时无法监听；

· 事件"推荐链接注册"需在被推荐人完成注册时上报（携带推荐人标识），用于转化统计与奖励发放；

· 交付团队提供问卷与推荐事件的埋点规范。

预期效益参考

公开好评量与推荐注册量提升 2-3 倍（行业参考）；推荐获客成本仅为付费广告的几分之一，且信任起点更高。

低分拦截路径每月在公开差评发生前挽回一批服务问题——防御价值不亚于增长价值。

场景 9｜ZenWatts 积分到期与兑换提醒

第二批 · 快赢 忠诚度 · 复购 到期日属性触发 · 三段提醒 · App Push + Email

积分到期前 30 天开始三段提醒，把"快过期的积分"变成扩展电池与配件的兑换动力——积分运营本身就是交叉销售。

旅程编排示意图
业务痛点

ZenWatts 积分可直接兑换扩展电池等产品、有效期 12 个月——但兑换全靠用户自己想起来打开积分商城。

快到期的积分是一笔"沉睡的兑换动力"：不提醒，静默清零、被感知为损失；提醒到位，就是客单最高的兑换与复购触发器。

旅程组件配置
  • 开始组件：属性"积分批次到期日 T-30 触发"且"积分余额 ≥ 最低兑换门槛"（可再次进入，间隔 30 天，覆盖多批次积分）
  • 提前退出：事件"积分兑换"→ 立即退出
  • 可发送时间 18:00–21:00 + App Push（T-30）：到期预告——变量下发积分余额与可兑清单（"你的积分 30 天后到期，已够抵扣一块扩展电池"）
  • 等待事件 14 天：监听"积分兑换"→ 已兑换退出 / 未兑换继续
  • 可发送时间 + Email（约 T-16）：兑换指南 + 完整可兑清单
  • 等待事件 9 天：监听"积分兑换"→ 已兑换退出 / 未兑换继续
  • 可发送时间 + App Push（约 T-7）：最后提醒（"积分 7 天后清零"）
  • 等待事件 5 天：监听"积分兑换"→ 结束
  • 转化统计：监听"积分兑换"，统计时间 7 天（兑换行为集中在提醒后一周内）
  • 埋点要求：属性"积分余额""最近批次到期日"（日期偏移触发）；事件"积分兑换"（携带兑换品类与积分数）
预期效益参考

积分核销率提升至 1.5–2 倍（行业参考）；这是数据依赖最小的快赢旅程——两个属性 + 一个事件即可上线。

场景 10｜新订阅者欢迎旅程

旅程编排示意图
业务痛点

该品类从"想买"到"下单"普遍要 2–8 周：算回本、看测评、等促销。

订阅者是主动留下联系方式的高意向人群，若只收到不定期群发，前两周的热度就白白冷却——同品类头部案例中，欢迎序列正是自动化体系的第一块基石。

旅程组件配置
  • 开始组件：事件"订阅 Newsletter / 注册账号"触发（一次性事件，不可再次进入）
  • 提前退出：事件"订单支付成功"→ 立即退出
  • Email 1（即时）：欢迎 + 订阅礼（首单权益、本地仓与质保介绍）
  • 等待 2 天 → 可发送时间 09:00–21:00 + Email 2：本地政策与收益科普（回本测算、容量选购指南）
  • 等待事件 3 天：监听"浏览商品页 / 加入购物车"，区分意向
  • 有意向路径：可发送时间 + Email——容量选购对比 + 真实用户评价
  • 未浏览路径：可发送时间 + Email——真实用户案例故事（安装前后电费对比）
  • 等待事件 5 天：监听"订单支付成功"→ 已购退出 / 结束（转入常规活动人群，长决策周期由新品与大促活动接力）
  • 转化 + 收入统计：监听"订单支付成功"，统计时间 7 天（对齐旅程跨度约 10 天）
