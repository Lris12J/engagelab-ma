业务洞察

1硬件是入口，App 是收入：三条收入曲线的转化时点都在设备事件上

影腾的摄像机以百元级价格经拼多多、天猫、京东与抖音售出，App 承担三条收入曲线：开屏与插屏广告随日活起伏，云录像按套餐付费，4G 室外机的流量套餐按周期续费。IoT 应用的广告变现以开屏与插屏为主（Taku × TopOn《2025H1 全球应用广告变现报告》），广告收入因此是日活的函数，而日活取决于用户被什么理由打开 App。三条曲线的共同点是转化时点落在设备的真实事件上——告警发生、余量见底、到期日、设备离线——而不在运营日历上。

01

旅程 1｜广告展示机会分层放大

广告收入直接相关日活与广告展示分群进入 · 每日重判 · App Push 自定义消息 · 效果在广告平台报表按组验收

默认分支不改任何现有广告位。增量来自两处：高活跃未付费用户加开激励视频入口，旅程 2、3 拉回的每次打开都是一次开屏展示。给新用户或付费用户少投插屏，只作 10% 对照组的 A/B。

建议渠道：App Push 自定义消息　｜　触发方式：用户分群「已绑定设备用户」，每日重新判定　｜　退出条件：解绑全部设备即退出

旅程编排示意图
业务痛点
  • 广告平台决定每次展示投什么，但制造不了一次打开，也不知道谁是付费用户、谁绑定第 3 天
  • 激励视频与插屏的 eCPM 在国内长期高于开屏，而激励视频需要一个用户主动进入的入口
  • 运营动作对广告收入的影响，必须能在贵司每天在看的广告平台报表里按人群拆出来
旅程组件配置
  • 开始组件：用户分群「已绑定设备用户」，发布时全量进入，之后满足条件即进入；排除已退订用户
  • 再次进入：退出后可再次进入（单实例），间隔 1 天——每日按最新属性重新判定分支
  • 提前退出：事件「解绑全部设备」
  • 转化统计：事件「App 启动」（SDK 自带），监听窗口 1 天；广告收入不在 MA 内统计
  • 条件分支：属性「近 7 天打开天数」大于等于 5 且「云录像状态」等于未开通 → 激励入口分支；属性「测试分组」等于实验组 且「绑定天数」小于等于 7 → A/B 分支一；属性「测试分组」等于实验组 且「云录像状态」等于有效 → A/B 分支二；默认 → 结束，App 沿用本地广告配置
  • App Push 自定义消息一：JSON 透传字段在现有开屏与插屏之上开启发现页与回放页的激励视频入口，奖励类型与额度由贵司定义（云录像试看天数或流量赠送）；App 端读取后交给广告聚合 SDK 的流量分组，不占通知栏
  • App Push 自定义消息二（A/B）：绑定不满 7 天的实验组，保留冷启与热启开屏、关闭插屏
  • App Push 自定义消息三（A/B）：付费用户实验组，插屏改为激励视频入口
  • 对照组与验收：属性「测试分组」等于对照组的用户走默认分支，保持现状；App 把该属性作为自定义流量分组键值传给广告聚合平台，广告平台报表即可按实验组与对照组拆分收益，两组 A/B 以 7 日留存与 7 日人均广告收入净额判定，是否保留由贵司决定
  • 等待：1 天后结束，次日重新进入并重判
  • 全局频控：自定义消息按消息类型单独设限，不占通知消息额度；透传字段只控制样式启用与频次，不涉及关闭方式等法定要求
  • 埋点：绑定天数、云录像状态、测试分组由贵司账户系统写入用户属性；近 7 天打开天数由 SDK 的 App 启动事件聚合；广告展示次数可选上报（广告 SDK 展示回调），只作过程指标
预期效益参考

日活 +4.7–9.3%（相对，EngageLab 同行业客户实测）

广告收入 = 日活 × 人均打开次数 × 每次打开的广告展示 × eCPM ÷ 1000；收入验收在广告平台报表按测试分组拆分，MA 侧只看打开与留存。

02

旅程 2｜看家日报

见效最快日活与广告展示分群进入 · 每日固定时段 · Webhook 取数 · App Push 通知消息

给用户一个告警之外的打开理由：每晚用 Webhook 取当日真实事件数生成日报，「今日家中 3 次动态」直达回放。无事件且近期活跃的用户不发，无事件但三天未打开的用户收到「今日一切正常」。

建议渠道：App Push 通知消息　｜　触发方式：用户分群「已绑定且至少一台设备在线」，每日进入　｜　退出条件：关闭看家日报即退出

旅程编排示意图
业务痛点
  • 没有告警的日子，用户没有打开 App 的理由，当日广告展示为零
  • 与用户家里实际情况无关的定时推送，点击率随发送次数衰减
  • 日报的时点要落在用户回家之后，需要按终端时区而非组织时区
旅程组件配置
  • 开始组件：用户分群「已绑定且至少一台设备在线」；进入条件排除属性「看家日报开关」等于关闭的用户
  • 再次进入：退出后可再次进入（单实例），间隔 1 天
  • 提前退出：事件「关闭看家日报」
  • 转化统计：事件「App 启动」（SDK 自带），监听窗口 12 小时
  • 可发送时间：终端时区 20:30–21:30，放在 Webhook 之前，当日事件数在该时段内取值
  • Webhook：向贵司 IoT 视频平台取当日告警事件数与在线设备数，返回值作为变量与分支依据；请求失败时事件数为空，走默认分支不发送
  • 条件分支：当日事件数大于 0 / 事件数为 0 且属性「最后打开 App 时间」距今超过 3 天 / 默认（当日无事件且近期活跃，不发）
  • App Push 通知消息一：「今日家中 {{事件数}} 次动态」，深度链接到当日回放；事件数取自 Webhook 返回值
  • App Push 通知消息二：「今日一切正常，{{在线台数}} 台设备在线」，深度链接到设备列表
  • 交接：本旅程只发当日内容；连续多日未打开的用户由旅程 3 按沉默天数承接
  • 埋点：告警事件与在线状态由 IoT 视频平台提供查询接口；日报开关为 App 内设置项写入用户属性
预期效益参考

与旅程 1 合并计入日活提升 +4.7–9.3%（相对）

按用户实际事件生成的推送属于分层定向，公开基准下点击率约为全量群发的两倍（5% vs 2.5%）。

03

旅程 3｜沉默用户分层召回（7 / 14 / 30 天）

日活回收沉默召回属性触发 · 三档分层 · Webhook 取设备状态 · App Push 通知 + SMS 兜底

召回的对象限定为设备仍在线、App 却沉默的用户。三档内容不同：一周用本周动态次数，一周没有任何动态的改发设备健康周报（电量、信号、流量）；两周用看家模式与新功能；一个月以上加短信兜底，覆盖已卸载 App 的人。

建议渠道：App Push 通知消息 · SMS　｜　触发方式：属性「最后打开 App 时间」距今超过 7 天且在线设备数不少于 1　｜　退出条件：App 启动即退出

旅程编排示意图
业务痛点
  • 设备在线但 App 一个月未打开，多半是告警推送已被忽略或关闭
  • 长期沉默用户是广告展示基数里最大的一块可回收人群
  • 30 天以上的沉默用户可能已卸载 App，通知到不了，需要短信兜底
旅程组件配置
  • 开始组件：属性「最后打开 App 时间」距今超过 7 天 且 属性「在线设备数」大于等于 1；进入条件加上限 90 天，避免发布首日存量用户一次涌入；排除已退订用户
  • 再次进入：退出后可再次进入（单实例），间隔 7 天，最多进入 3 次
  • 提前退出：事件「App 启动」（SDK 自带）
  • 转化统计：同一事件，监听窗口 1 天
  • 条件分支一：属性「最后打开 App 时间」距今 7–13 天 / 14–29 天 / 30 天及以上
  • 条件分支二（7–13 天）：属性「近 7 天告警次数」大于 0 → App Push 通知消息「本周家中 {{近 7 天告警次数}} 次动态待查看」；等于 0 → Webhook 向 IoT 视频平台取各设备电量、信号与流量余量 → App Push 通知消息「本周无动态，设备健康周报」，字段取自返回值，请求失败改发设备在线文案

  • 条件分支三（30 天及以上）：属性「短信接收状态」两分支——已同意走 SMS 模板消息，未同意走 App Push 通知消息，内容一致：设备在线、家人共享入口
  • 可发送时间：终端时区 19:00–21:30，放在每条消息之前
  • 埋点：最后打开时间由 SDK 自带；近 7 天告警次数由贵司系统按设备事件聚合后写入用户属性

召回推送点击率 5–7%

旅程 4｜云录像开通：告警发生的当下

付费收入直接产出云录像转化设备事件触发 · 先观察再触达 · 高频取优惠码 · 低频换试看 · 应用内消息 + App Push 通知

云录像最有说服力的时刻是告警刚发生、用户正在看画面：此时用应用内消息说「这次动态没有保存到云端」，不再占一条通知。次日再用近 7 天真实动态次数跟进，高频告警用户取优惠码，低频用户改用看激励视频换云录像试看。

建议渠道：应用内消息 · App Push 通知消息　｜　触发方式：事件「告警事件触发」且云录像状态为未开通　｜　退出条件：购买云录像即自动退出

旅程编排示意图
业务痛点
  • 云录像的价值在告警发生时最直观，隔天的促销消息说服力已经衰减

  • 开始组件：事件「告警事件触发」（人形检测 / 逗留 / 强拆）+ 用户属性过滤「云录像状态」等于未开通；事件属性携带设备 ID 与事件类型
  • 再次进入：退出后可再次进入（单实例），间隔 7 天，最多进入 4 次
  • 提前退出：事件「购买云录像」
  • 转化统计：同一事件，监听窗口 3 天；收入统计：同一事件 + 订单金额属性，监听窗口 3 天
  • 等待事件：30 分钟内等待「查看实时画面或回放」，一个事件分支 + 超时默认分支
  • 应用内消息：已查看分支，用户当前在 App 内或下次打开时展示「刚才这次动态未保存到云端，开通后 {{套餐保留天数}} 天内随时回看」，直达套餐页；保留天数取自套餐属性
  • 等待：1 天 → 可发送时间 → App Push 通知消息「近 7 天家中 {{近 7 天告警次数}} 次动态仅保存在本地」，次数取自属性
  • 等待：3 天 → 条件分支：属性「近 7 天告警次数」大于等于 3 走优惠分支；默认（不满 3 次）走试看分支
  • Webhook：向贵司优惠券系统取首购优惠码与有效期，写入消息变量；无券返回时不发本条
  • App Push 通知消息（优惠分支）：高频动态用户专属首购优惠，有效期取自 Webhook 返回值
  • App Push 通知消息（试看分支）：「看一段激励视频，换 {{试看天数}} 天云录像试看」，深度链接到旅程 1 开启的激励视频入口；试看天数取自奖励配置属性，贵司未提供奖励机制时不发本条
  • 可发送时间：终端时区 9:00–21:00，放在三条通知之前
  • 合规约束：视频与人像影像不同步到 MA，只同步事件类型、次数与状态
  • 埋点：告警事件与查看行为由 IoT 视频平台与 App 上报；云录像状态与购买事件由订单系统回写

旅程 5｜云录像到期续费（前 7 天 / 前 1 天 / 后 3 天）

  • 过期后云端录像的保留期是真实的最后期限，也是最有效的续费理由

  • 提前退出：事件「云录像续费成功」

  • 条件分支一：属性「自动续费」已开启 → App Push 通知消息「将于 {{到期日}} 自动续费」后结束；未开启进入提醒序列

旅程 6｜4G 流量余量与套餐续费

4G 室外机专属续费与在线率设备事件触发 · 多实例按设备并行 · App Push 通知 + SMS

太阳能 4G 室外机装在没有 WiFi 的地方，流量用尽就是离线。一户多台时每台各有套餐周期，这条旅程按设备开独立实例：余量、充值与离线都按设备各自计，充了 A 台不会让 B 台的提醒消失。

建议渠道：App Push 通知消息 · SMS　｜　触发方式：事件「流量余量低于 20%」（按设备）　｜　退出条件：该设备流量充值成功即退出对应实例

旅程编排示意图
业务痛点
  • 流量用尽的设备不再产生告警，用户往往到需要回看时才发现
  • 一户多台 4G 机的套餐周期不同，单实例旅程只能提醒其中一台
  • 充值入口在 App 或小程序，提醒必须直达对应设备的充值页
旅程组件配置
  • 开始组件：事件「流量余量低于 20%」由贵司 4G 流量服务平台回传，事件属性携带设备 ID、套餐名与余量
  • 再次进入：可同时多次进入（多实例，按业务并行），并发上限 5，两次进入最短间隔 7 天——每台 4G 摄像机一个实例
  • 提前退出：事件「流量充值成功」，属性过滤设备 ID 等于本实例值，只退出对应实例
  • 转化统计：同一事件，监听窗口 2 天；收入统计：同一事件 + 充值金额属性，监听窗口 2 天
  • App Push 通知消息一：「{{设备名}} 流量剩余 {{余量}}%，用尽后设备离线」，深度链接到该设备的充值页；文案附「开通自动充值」入口（如贵司提供），减少下一周期对提醒的依赖
  • 等待：2 天 → 条件分支：属性「短信接收状态」——已同意走 SMS 模板消息，未同意走 App Push 通知消息，内容一致
  • 等待：3 天 → 等待事件：5 天内等待「设备离线」（设备 ID 匹配本实例）——离线分支发 App Push 通知消息「{{设备名}} 已因流量用尽离线」；未离线走默认分支结束
  • 可发送时间：终端时区 9:00–21:00，放在每条消息之前
  • 交接：旅程 7 对 4G 机先取流量余量，余量为零的离线一律由本旅程承接
  • 埋点：流量余量与充值成功由流量服务平台以事件回传或 Webhook 取数，第 1 周二选一
预期效益参考

用尽前充值率提升、因流量离线的设备台数下降（对照组比较）

流量续费收入 = 提醒覆盖设备数 × 用尽前充值率 × 套餐单价；保住在线的设备同时是旅程 2 与旅程 4 的触达对象。

  • 设备离线期间用户也不会打开 App，日活与广告展示同步归零

  • 开始组件：事件「设备离线超过 72 小时」由 IoT 视频平台回传，事件属性携带设备 ID 与设备类型
  • 再次进入：可同时多次进入（多实例，按业务并行），并发上限 5，两次进入最短间隔 14 天
  • 提前退出：事件「设备上线」，属性过滤设备 ID 等于本实例值
  • 转化统计：事件「设备上线」，监听窗口 7 天

  • App Push 通知消息：4G 机给电量与信号的排查指引，WiFi 机给路由与电源的排查指引，均深度链接到设备页与帮助

旅程编排示意图
业务痛点
  • 太阳能板被遮挡或朝向不对，电量会在连续阴雨天一路下降直到离线
  • 离线之后再提醒，用户已经错过一段没有录像的日子
  • 一户多台室外机的电量各不相同，提醒必须按设备分开
旅程组件配置
  • 开始组件：事件「电量低于 20%」由 IoT 视频平台回传，事件属性携带设备 ID、设备名与当前电量；用户属性过滤「设备类型」包含太阳能机
  • 再次进入：可同时多次进入（多实例，按业务并行），并发上限 5，两次进入最短间隔 14 天——每台太阳能机一个实例
  • 提前退出：事件「电量恢复至 50% 以上」，属性过滤设备 ID 等于本实例值，只退出对应实例
  • 转化统计：同一事件，监听窗口 5 天
  • 可发送时间：终端时区 9:00–21:00 → App Push 通知消息一：「{{设备名}} 电量 {{电量}}%，请检查太阳能板是否被遮挡」，深度链接到设备页与安装指引
  • 等待：2 天 → 条件分支：属性「短信接收状态」——已同意走 SMS 模板消息，未同意走 App Push 通知消息，内容一致：电量仍在下降，用尽后设备将离线
  • 交接：本旅程只在离线前介入；设备仍离线 72 小时后由旅程 7 承接排查指引，流量为零的离线由旅程 6 承接
  • 埋点：电量事件由 IoT 视频平台回传；设备类型为绑定时写入的设备属性
