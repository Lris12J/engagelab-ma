业务洞察

1Typhur 的产品结构，与用户运营的四个切入点

Typhur 的单用户价值是三段链路：首台设备 → 配件与耗材 → 第二、第三台设备。 第一段由广告与产品力决定，后两段取决于用户是否真的把设备用起来——而这只有 App 与设备侧数据看得见。 下表按这条链路排开在售产品线。

切入点 1 · 购前长决策
  • 空气炸锅与无线探针属重研究品类，访客首次到站很少直接下单，决策周期常以周计
  • 官网已有「首单 9 折」邮箱订阅入口与 Refer-a-Friend 推荐计划，留资名单具备承接培育的基础
  • 弃购是这一段最大的单点折损，且移动端明显高于桌面端
切入点 2 · 购后身份获取
  • 亚马逊与线下买家的身份不在品牌手里，这是全案的枢纽环节
  • 设备不装 App 也能用（Sync 有屏、Dome 有面板、InstaProbe 是纯硬件），绑定必须给理由，不会自动发生
  • 不注册就没有自有触点，不绑定就没有设备侧数据——旅程 4 至 7 全部落空
切入点 3 · 烹饪使用留存
  • 厨电最大的隐性流失不是退货，是买回家用过两次就收进柜子
  • 首次成功烹饪是价值兑现的拐点，其后的使用频次决定配件复购与生态交叉的基数
  • App 已具备食谱、AI 食谱生成与一键载入程序的能力，缺的是把用户带回来的触发机制
切入点 4 · 复购与生态交叉
  • 官网在售 11 个配件件号，其中仅 3 个是会用完的真耗材（真空袋、制冰机清洁剂、替换刷头），其余为一次性配件
  • 因此这一段的关键是推荐时机而非推荐频次——用户用过几次才知道自己缺什么
  • 已经用出结果的单设备用户，通常比新客更容易接受第二台设备
四个切入点共同的前提：用户池只能靠用户主动建立，不能靠平台订单

亚马逊的卖家政策明确规定：卖家不得为营销或推广目的联系买家； 为履约获得的买家信息只能用于履约、用后需删除，也不得用于建立买家邮箱名单。 这意味着平台买家无法通过订单数据进入 MA。

唯一合规路径是用户扫码主动完成产品注册或 App 注册并勾选同意。 方案中所有「把平台买家转为自有用户」均指这条路径，不涉及订单信息的导出或反查。 这也决定了旅程 3 的优先级——它决定其余八条旅程能覆盖多少人。

数据整合

3数据整合：把独立站、App、设备与产品注册收敛到同一个用户身份

MA 不替代现有的独立站、App 与设备云，而是在其之上做统一身份、跨渠道编排与触达执行。 四类数据源归到同一个用户身份下之后，旅程才能按真实使用状态分流，而不是按购买日期群发。

独立站（typhur.com / eu.typhur.com）
  • 订单侧：下单、支付、发货、送达、退款、退货申请 —— 通过订单系统 Webhook 接入
  • 行为侧：机型页浏览与停留、配件页浏览、加购、发起结账 —— 通过 Web SDK 接入
  • 邮箱订阅、Web Push 授权、Refer-a-Friend 推荐关系
Typhur App
  • 注册、登录、设备绑定（购后全部旅程的关键分流依据）
  • 食谱浏览与收藏、AI 食谱生成使用、烹饪程序载入
  • 食谱下发到设备、自定义烹饪参数的保存与调用
  • 注册、登录、绑定属 SDK 接入后即可上报的基础事件
设备云（探针 / 空气炸锅 / 烤箱）
  • 烹饪开始与完成、烹饪时长、程序类型（低温慢煮 / 空气炸 / 烟熏等）
  • 累计烹饪次数（配件复购与生态交叉的触发依据）
  • 固件版本与升级结果、异常码 —— 通过 Server API 同步
产品注册 / 客服 / 履约
  • 包装内二维码产品注册：机型、序列号、购买渠道、延保登记与接收同意
  • 客服工单、退换货申请、保修申请
  • 满意度反馈与公开评价提交状态
  • 配件库存与型号适配表（供复购旅程发送前实时取值）
接入工作量

九条旅程共需 16 个事件、12 个用户属性。工作量分两段，下面这个数字只是第一段：

  • MA 侧接入：1–2 名开发 3–5 人日——独立站加载 Web SDK、App 集成 SDK、按交付团队给的字段清单上报
  • 贵司系统侧改造：需另行评估。设备云要新增烹饪事件外发，以及「累计烹饪次数 / 最后烹饪时间」的聚合。产品注册页要补同意勾选与序列号回传。这几项跨设备云、注册页、独立站三个系统，工作量取决于现有接口成熟度
  • 建议第 1 周先做接口盘点，再确定第二段的排期。交付团队提供完整埋点方案与联调支持
消息里的内容是实时的
  • 弃购提醒带的是购物车中的真实机型、价格与图片
  • 配件推荐的适配清单与库存是发送当下有效的，不会推到断货件号
  • 延保提醒里的剩余天数是这台设备的真实数据

01

旅程 1｜独立站访客培育与首单转化

名单资产激活购前决策订阅事件触发 · 品类三分流 · Email + Web Push

按站内浏览过的品类分三路发选购内容，而不是给所有留资用户发同一封。第 7 天仍未下单的，把推荐降到 59 美元的入门探针——先让人用上一次，比反复劝说买 340 美元的机器有效。

建议渠道：Email · Web Push　｜　触发方式：事件「邮箱订阅」或「账号注册」　｜　退出条件：订单支付成功即自动退出

旅程编排示意图
业务痛点
  • 高客单重研究品类，决策周期以周计，首访下单极少
  • 留资名单若只在促销节点使用，整个决策期是空白的
  • 未表达品类偏好的访客，用统一内容触达等于浪费一次机会
旅程组件配置
  • 开始组件：事件「邮箱订阅」或「账号注册」触发进入
  • 再次进入：不可再次进入（订阅与注册对同一用户仅发生一次）
  • 提前退出：事件「订单支付成功」
  • 转化统计：事件「订单支付成功」，监听 7 天（首条至末条消息跨度 6 天）
  • 收入统计：同一事件 + 订单金额属性，监听 7 天
  • 等待：1 天 / 2 天 / 4 天三段固定等待
  • 条件分支：属性「最近浏览品类」三分支——温度探针 / 空气炸锅与烤箱 / 未浏览
  • Email：浏览过的机型名与价格通过变量插入，发送前实时取值
  • Web Push：承接未表达品类偏好的一支
  • 可发送时间：终端时区 9:00–21:00，放在每条跨天后发出的消息之前
  • 埋点：邮箱订阅、账号注册、页面浏览、订单支付成功由 Web SDK 与订单 Webhook 上报
预期效益参考

首单转化 +2 – 5%（绝对值）

同时把匿名访客转为有身份的名单，扩大后续所有购后旅程的进入池。

02

旅程 2｜高客单弃购挽回

见效最快结账转化结账事件触发 · 多实例最新覆盖 · Web Push + Email + SMS

高客单弃购不是忘记，是结账页临时冒出的保修、退货、运费疑虑，因此三轮内容全部用于消除顾虑，全程不加折扣。采用多实例·最新覆盖：每次新的结账都用最新购物车重新计时，不再用「7 天冷却」漏掉意向。

建议渠道：Web Push · Email · SMS　｜　触发方式：事件「发起结账」　｜　退出条件：订单支付成功即自动退出

旅程编排示意图
业务痛点
  • 移动端弃购率明显高于桌面端，而高客单决策多发生在移动端
  • 疑虑集中在保修、退货与运费，商品页往往没有正面回答
  • 用折扣挽回会反向训练用户等促销，侵蚀原价成交
旅程组件配置
  • 开始组件：事件「发起结账」触发进入
  • 再次进入：多实例 · 最新覆盖，并发上限 1、达上限替换最早实例
  • 提前退出：事件「订单支付成功」
  • 转化统计：事件「订单支付成功」，监听 1 天（首条至末条消息跨度约 22 小时）
  • 收入统计：同一事件 + 订单金额属性，监听 1 天
  • 等待：30 分钟 / 2 小时 / 22 小时三段固定等待
  • Web Push：结账发生在独立站，用于 30 分钟后的即时拉回
    Email：机型、价格、图片、库存通过变量插入，取值来自结账事件或发送前 WebHook
  • 条件分支：属性「手机号不为空 且 短信接收同意为真」决定走 SMS 还是 Email
  • 可发送时间：仅 22 小时后的两条消息加，SMS 一支为终端时区 9:00–20:00
预期效益参考

弃购挽回率 8 – 12%

旅程跨度不到 24 小时，是全案中最容易独立核算 ROI 的一条。

03

旅程 3｜开箱引导：App 绑定与产品注册

优先级最高购后身份获取送达 / 注册触发 · 先观察再触达 · Email + Web Push

设备不装 App 也能用，所以绑定必须给出 App 独有的理由——远程监控、分步指导、食谱下发、延保与安全通知。整条不用 App Push（对象正是尚未绑定的人），并按设备序列号开多实例，先后买两台互不覆盖。

建议渠道：Email · Web Push　｜　触发方式：事件「订单送达」或「产品注册提交」　｜　退出条件：设备绑定成功即自动退出

旅程编排示意图
业务痛点
  • 设备不装 App 也能完成基本烹饪，绑定率不会自动上去
  • 平台与线下买家不注册，就完全没有自有触点
  • 独立站买家虽有邮箱，但不绑定 App 就没有设备侧数据
旅程组件配置
  • 开始组件：事件「订单送达」或「产品注册提交」触发进入

合规与安全

6合规与数据安全（北美 · 欧洲 · 澳洲三市场）

三个法域对营销消息的同意口径各不相同，叠加亚马逊自身的卖家规则，合规约束比单一市场品牌复杂一档。 本节把平台能力与业务方需落实的动作分开列出—— MA 提供执行工具与护栏，同意采集与内容合规的主体责任仍在业务方。

优先级最高的一条：平台买家信息不进入 MA

亚马逊卖家政策明确规定：卖家不得为营销或推广目的联系买家； 为履约目的获得的买家地址、电话等信息只能用于履约，处理完成后需删除， 也不得用于建立买家邮箱名单或与第三方共享。

因此平台买家进入 MA 只有一条路径：扫描包装内二维码，在 Typhur 自有的注册页主动提交身份并勾选同意。 进入 MA 的是这份自有身份与同意记录，不涉及订单联系方式的导出、匹配或反查。

测试期第 1 周需先确定注册页的同意勾选、法域标识与偏好选项——它决定了后续所有旅程的可用人群与渠道。

三市场合规要点（业务方落实）
  • 美国 · Email / CAN-SPAM：真实发件人与主题、可识别的实体地址、一键退订且 10 日内生效
  • 美国 · SMS / TCPA：营销短信需明示书面同意；每条含 STOP 退订说明；遵守收件人本地 8:00–21:00 时段；需完成 10DLC 登记
  • 美国 · 州级隐私法：加州等州要求提供「不出售 / 不共享个人信息」的选择权，该状态需作为用户属性进入 MA
  • 英国与欧盟：GDPR 与 ePrivacy / PECR 要求营销邮件与 Web Push 事前同意；已购客户同类商品的软性 opt-in 各国口径不同，需按国别配置
  • 澳洲：Spam Act 2003 要求同意、标明发送方身份、提供可用的退订方式
  • 以上为业务方需落实的合规动作，MA 提供对应的执行与校验工具，不替代法务意见
平台数据安全与认证
  • 已通过 GDPR 与 SOC 2 认证
  • 全链路 TLS 传输加密，VPC 网络隔离，存储层与传输层分离
  • PII 字段脱敏存储与访问，基于角色的权限控制（RBAC）
  • 可协助客户满足各目标市场本地数据保护法规要求；数据中心可按客户安全需求灵活扩展
  • 设备侧进入 MA 的是烹饪次数、程序类型、固件版本等状态属性，不涉及用户在 App 内上传的照片等内容数据
运营护栏
  • 全局频控：按用户设置每日 / 每周 / 每小时消息上限，跨旅程统一生效——九条旅程并行时自动协调，不会叠加打扰
  • 可发送时间：按终端用户时区限制时段，直接承接美国短信的时段要求，也解决三个法域时差问题
  • 提前退出：完成目标行为后立即停止后续触达
  • 内容预览：发送前支持样式预览
  • 消息记录：发送记录保留 60 天，可追溯
关于产品安全与召回通知
加热类厨电存在产品安全通知与召回的合规义务，这类消息属事务性内容， 与营销消息在同意口径与用户预期上均不相同，应使用独立模板、独立文案口径。 平台的频控是按用户生效的全局频控，跨旅程统一协调、不区分消息类型， 因此设定每日上限时应为安全类通知预留额度。 这也是产品注册环节的一项实际价值：只有完成注册的用户，才有可触达的安全通知通道。

落地计划

84 周测试计划 · 九条旅程分三批上线

埋点总量 16 个事件、12 个用户属性。MA 侧接入 1–2 名开发 3–5 人日； 设备云的事件外发与累计次数聚合、产品注册页的同意勾选与序列号回传属贵司系统侧改造，需在第 1 周盘点后另行排期。 埋点第 1 周一次性完成，不做分期；分批的是旅程上线顺序。

1第 1 周 · 对齐 + 接入
  • 对齐北极星指标：产品注册 / App 绑定率、首次成功烹饪完成率、月活跃烹饪用户数
  • 核对存量池的邮箱有效率、Web Push 授权率与短信同意率，用真实数字替换方案中的触达测算
  • 确定产品注册页的同意勾选、法域标识与偏好选项
  • 对齐埋点范围：16 个事件、12 个用户属性；多实例旅程还需设备序列号随事件上报，作为实例变量
  • 开通 Email / SMS 通道，完成发信域名与短信 10DLC 登记
2第 2 周 · 第一批上线
  • 枢纽三条：旅程 3（绑定与注册）、4（首次烹饪）、2（弃购挽回）
  • 前两条决定后续旅程能覆盖多少用户，第三条见效最快、最容易独立核算 ROI
  • 配置进入条件、再次进入模式（旅程 2/3/4 为多实例，发布后不可改）、提前退出、转化与收入统计、全局频控
  • Email / SMS / Web Push 模板搭建，三个法域的必备合规要素逐条核验
3第 3 周 · 第二批上线
  • 第二批四条：旅程 1（购前培育）、5（沉默唤醒）、6（配件复购）、9（评价与推荐）
  • 存量买家按属性条件进入旅程 5、6、9，核对各条件分支的实际人数分布
  • 观察各旅程的发送 / 送达 / 点击 / 转化漏斗与退订率
  • 对比进入旅程组与对照组的绑定率、首次烹饪完成率与配件复购率
4第 4 周 · 第三批 + 复盘
  • 交叉与活动两条：旅程 7、8（旅程 7 依赖第 2–3 周积累的绑定与烹饪数据，故排在第三批）
  • 按最近的节令日排期旅程 8 的首轮投放
  • 复盘三周数据，固化高效旅程、下线低效分支
  • 放开全局频控上限至数据支持的水平，并为安全类通知预留额度
  • 输出下一季度的持续运营路线图
贵司侧需要投入的人力
  • 运营 1 人：全程参与，负责旅程内容与分批验收
  • 开发 1–2 人：第 1–2 周集中投入，之后转为按需支持
  • 设计 0.5 人：Email 与 Push 模板，第 2 周集中
  • 法务 / 合规：第 1 周确认三个法域的同意口径与文案要素
效果怎么算才作数
  • 每条旅程按进入组与对照组核算，不看旅程内的绝对转化数
  • 收入类旅程（2 / 6 / 7 / 8）直接读旅程的收入统计，与对照组差值即增量
  • 非收入类（3 / 4 / 5）读目标事件完成率，再按后续旅程的转化链折算
  • 4 周只够读出旅程 2、3、4 的稳定数据；跨度长的旅程需要一个完整季度

分批顺序按「当前折损 × 落地难度」排定，可根据贵司第 1 周核对出的真实数据调整。 若产品注册率的实际水平明显高于行业基准，第一批可与第二批对调，优先做复购与召回。
